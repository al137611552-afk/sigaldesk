# ADR-0007 多级别规则 = 有序条件链路 + 单一状态机

- 日期: 2026-08-28
- 状态: Accepted

## 背景
ARCHITECTURE §5 把多级别规则画成 `trend → setup → trigger` 三段式，配一台
`IDLE / TREND_OK / SETUP_ARMED / FIRED / COOLDOWN` 状态机。真要落地时有几处必须先定死，
否则每条规则的行为都会随实现细节漂移。

## 决策

### 1. 规则是**有序条件链路**，不是"三段式"专用结构
`conditions` 的顺序就是链路顺序，最后一条是扳机。段数任意：
- 长度 1 = M1 的单级别规则；
- 长度 3 = 经典三段式；
- 长度 4+ 也能表达。

**因此 M1 与 M2 共用一个模型、一个引擎**，不存在"单级别引擎"和"多级别引擎"两套东西。
状态机里真正的状态是 `stage`（已满足到第几段），`IDLE/ARMED/COOLDOWN` 只是给人看的投影。

### 2. 只有 `mode: state` 是**持续型**，只有它失效才回退
`window`/`event` 表达的是"最近发生过"和"刚刚发生"，都是瞬时的。
要求它们"仍然成立"会让链路永远推进不下去。
回退目标是**失效条件之前那一段**，不是一路退回 IDLE —— trend 还在、只是 setup 过期时，
应该退回 TREND_OK 继续等下一次机会。

### 3. TTL 数**扳机 bar 根数**，不接受时长
用墙钟的话，休市、午休与数据缺口都会白白消耗 TTL，回放与实盘就对不上了。
加载器直接拒绝 `ttl: 30m` 这种写法。

### 4. 冷却精确等于配置秒数，解冷那一根**继续参与判定**
第一版实现把解冷那一根"消耗"掉了（只解冷、不判定），结果实际冷却比配置多一根 bar，
而且多出的时长还随周期变化（5m 周期多 5 分钟，1h 周期多 1 小时）。已改。

### 5. 求值分**记账**与**判定**两步
- 记账：任何周期的 bar 收盘 ⇒ 求值挂在该周期上的条件，记进滚动日志。每根只求值一次。
- 判定：只有扳机周期的 bar 收盘才跑状态机。

**必须先把一批同时收盘的 bar 全部记完账再判定** —— 否则 15m(setup) 与 5m(trigger) 同刻收盘时，
扳机会读到上一根 setup 的结果，信号整整晚一拍。所以引擎入口是 `on_bars(批)` 而非 `on_bar(单根)`。

配套改动：`BarBuilder` 现在让**恰好落在桶边界的那根 1m 当场收盘**（墙钟分桶下它就是本桶最后一根），
而不是等下一根来触发桶切换。不改的话每条多级别规则都会晚一根，连 `role_bars` 与去重键都会错位。

### 6. 持久化只存"重算不出来的东西"
SQLite 里只存**状态机 + 条件日志 + 去重表**（外加信号表）。
指标缓存不存 —— 它可以由 BarStore 的历史重新喂出来（首次用到时整段回放），
存进去只会让快照又大又易腐。

重启流程因此分两条路，**不能混**：
- 无存档（首启）：`prime`，只喂指标与条件日志，不发信号 —— 否则等于把几十小时历史当实时报一遍。
- 有存档（重启）：`resume`，游标之前的只用于重建状态，游标之后的补判补报 —— 这就是"不丢报"；
  "不重报"由持久化的去重表兜底。

## 权衡
- 优点：一套模型覆盖 1~N 段，M1 规则不用改一个字就继续工作。
- 优点：引擎全部时间取自 `bar.close_ts`，不读系统时钟 ⇒ replay 与 live 天然逐条一致（红线）。
  这条有专门的单测：把 `time.time`/`datetime.now` 换成会爆炸的桩，整条链路仍要跑通。
- 代价：`window` 的 `within` 与 `ttl` 职责容易被混淆（前者管"能否推进过这一段"，
  后者管"armed 能撑多久"）。已写进 CLAUDE.md 并配单测说明。
- 代价：重启时新增的规则，在游标之前的历史不会被记账，要等积够新 bar 才可能触发。
  这是刻意的保守取舍 —— 总比一上线就按旧数据补报一堆信号好。

## 已知限制
- 跨标的的信号先后不是确定量（各标的状态独立），比对 replay 与 live 时须**按标的分组后再比**。
- 状态机不做跨合约迁移：换月当日新合约从 IDLE 起（ARCHITECTURE §3.4），已有单测覆盖。
