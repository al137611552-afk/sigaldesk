# ADR-0009 只读面板用无构建单页，不上 Vite/React

- 日期: 2026-08-31
- 状态: Accepted（**取代** ARCHITECTURE §7 中"前端 Vite + React + TS"的部分）

## 背景
ARCHITECTURE §7 原写"前端 Vite + React + TS + lightweight-charts"。真到 M3 要落地时，
开发机只剩 6.1G 磁盘、2 核 4G 内存，而 M3 的交付物是 **P0 只读面板**：
信号流、K 线回看、运行健康、质量统计。

## 决策
M3 用**无构建单页**：原生 JS + CSS，`lightweight-charts` 以单文件形式**内置进仓库**
（`src/sigdesk/web/static/vendor/`），由 FastAPI 直接 serve。不引入 node 工具链。

配套的一条设计约束：**凡是能算在服务端的就算在服务端**。
最典型的是 K 线上的信号标注 —— 第一版写在前端 JS 里，结果 M3 的验收
"图上标注的信号点与 SignalStore 记录逐条对得上"根本没法测。
改成 `/api/markers` 由服务端出标注点、前端只负责画，这条验收就变成了一个可单测的服务端不变量。

## 权衡
- 优点：部署就是一个 Python 进程，VPS 上不需要 node、不需要 build 产物跟着仓库走。
- 优点：面板的"逻辑"几乎都在 Python 侧，因此几乎都在测试覆盖里。
- 优点：省下 ~300MB 的 node_modules（磁盘只剩 6.1G）。
- 代价：偏离原架构。P1 规则 CRUD、P2 可视化编辑器的交互复杂度上来之后，
  原生 JS 会开始吃力，那时可能要重写前端。**这是明确接受的代价**，不是疏忽。
- 代价：`lightweight-charts` 是 vendored 的，升级要手动换文件（有版本号在文件头，可核对）。

## 已知限制
- 面板是**纯只读**：没有任何写端点。规则 CRUD 是 P1，可视化编辑器是 P2。
- 两种运行模式共用同一套端点：同进程（`watch.py --web`，健康与 SSE 有真数据）
  与独立只读（`serve.py`，只连 SQLite 与 Parquet）。后者的健康页如实显示"未接入实时引擎"，
  而不是假装一切正常。
- SSE 每个订阅者一个**有界**队列，满了丢它自己的旧消息 ——
  一个开着不管的浏览器标签页绝不能反压到行情处理上。
