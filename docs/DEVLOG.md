# DEVLOG

## 2026-09-04 — 规则引擎的平方复杂度（1m 扳机"跑不完"的真因）

用户把扳机换到 1m 后，`rule_eval.py breakout-long --rules-dir experiments/rules-retest`
跑不出来。第一反应是死循环，**不是** —— 是 O(n²)，只是常数大到看着像卡死。

### 排查过程里两次判断错了，记下来

1. 先怀疑 `EvalContext.stamps()/series()` 每次求值重建整列，加了 `IndicatorCache.column()`
   增量缓存。测下来**增速一点没变**（还是 3~4×/翻倍）。原因是我的 `column()` 结尾
   `return tuple(cur)` —— 把增长中的列表拷成元组，每次求值拷一遍，缓存等于白做。
2. 修完拷贝，合成基准**还是** 3.2×/翻倍。再查发现平方项在**我自己的基准**里：
   `bars[:i]` 每轮切一份 i 长度的序列。改成固定窗口喂就线性了。
   教训：**基准本身也要先证明它测的是被测对象。**

### 真因（三处，全在回测每根 bar 上重复付）

- `BarView.__init__` 给 store 里**每个**周期物化 `[b.close_ts for b in bars]` 再二分。
  为了 O(log n) 的二分先付 O(n)，而且规则用不到的周期也照付。面板派生九个周期 → ×9。
- `BarView.bars()` 每次 `tuple(seq[:cut])`，最多拷 MAX_BARS=5000 根。
- 每根 bar 里 `_context`（每个角色一次）+ `_role_bars` 各建一个视图 → 再 ×(角色数+1)。

1m 当扳机时 bar 数是 1h 的 60 倍，两边同时放大，于是只有加了 1m 条件才"跑不完"。

### 改法

`bars()` 返回只读前缀视图 `_Prefix`（持底层 list + 截断位置，**不拷贝**）；
list 引用构造时定死、二分用 `key=` 且按需算。消费方只用 `len` / 负下标 / 切片 /
迭代 / 真值，都能满足；`_Prefix` 还实现了 `__eq__` 以便和元组直接比较。

**INV-1 照旧成立**：越界下标 IndexError，切片夹在截断点内，看不到未来。

### 这个改动引入的新风险（真的踩到了）

不拷贝 = 持有底层 list 引用，于是裁剪如果就地 `del seq[:n]`，已发出的视图下标会
**整体错位：长度对得上、内容全错、不报错**。我先把裁剪改成"换一条新 list"，
自以为够了 —— 写回归测试时**测试红了**：`BarView` 存的是 series **字典**，
`bars()` 每次重新 `self._series.get(tf)`，照样跟着换到了新 list 配旧 cut。
最终把 (list 对象, 截断位置) 成对捕获、成对缓存才对。两条回归测试钉住这一点。

写测试写出真 bug，这次值回票价。

### 实测

| | 旧 | 新 |
|---|---|---|
| `rule_eval breakout-long`（6 标的、两个 1m 角色） | 84.9s | **10.6s** |
| 合成 32k 根表达式求值 | 9.19s | 0.67s |
| 引擎每翻倍增速 | 平方 | **2.0×（线性）** |

输出逐字不变：35 条、胜率 85.7%、超额 +0.0492%。全回归 851 passed，
`scripts/acceptance.py` 49/49，ruff / mypy 干净。


## 2026-08-28 — 立项 + M0-A 期货数据底座

### 设计定案
四项拍板：双线并行（期货+加密）、行情与交易通道分离、形态三档（指标/结构/插件，不做缠论）、
带 Web 界面的服务（Web 排到 M3）。产出 PRD / ARCHITECTURE / ROADMAP / CONVENTIONS + ADR-0001~0004。

### 数据源实测（最有价值的一段，全部写进 CLAUDE.md 坑列表）

对 Quote API 做了系统性探测，六个发现改变了设计：

1. **分钟线 `time_stamp` = 收盘时刻**，不是开盘时刻。
   依据：rb8888 各交易节首根标 09:01/10:31/13:31/21:01，末根标 10:15/11:30/15:00/23:00。
2. **返回数组末根恒为进行中 bar**，数值会变（同一分钟两次采样 volume 3037→5190）。
   ⇒ 判据统一为 `closed ⟺ close_ts <= now`，不靠"是不是最后一根"。
3. **日线 `time_stamp` 是交易日的 UTC 零点**，与分钟线语义不同 ⇒ 分路径转换。
4. **`GET /varieties/main` 服务端 500**，主力映射改用 `main-by-date`。
5. **接口无加密数据**（搜 BTC 命中美股/ETF），加密必须自接交易所 —— 印证双线架构。
6. **两个 K 线接口分工不同**：`by-count` 是唯一能取当日盘中数据的接口；
   `by-timerange` 不含当日但支持复权、无数量限制，是权威归档。

### 推翻了自己的一条设计
原 ARCHITECTURE 写"回测用 8888 主力连续"。实测：rb8888 同一时段 1m 数据在两接口间
**272/345 根不一致，其中 75 根价格不一致**；而真实合约 rb2610 仅 2/345 根微差。
⇒ 改为：一切用真实合约，连续序列由本系统按 `main-by-date` 自行拼接。已更新 ADR-0002 与架构文档。

### 分桶规则（实测导出，比原设想简单）
原以为要按 session 内累计计数，实测为**纯墙钟对齐 + 跳过空桶**：
`bucket_close = ceil(close_ts / period) * period`。
决定性证据：rb 60m 日盘序列为 `10:00 / 11:00 / 12:00 / 14:00 / 15:00` ——
12:00 那根只含 11:00-11:30 的 30 分钟数据，13:00 因无交易被跳过。

### 已实现
`core/`（models / timeframes / calendar / registry）、`feed/quote_api.py`、
`store/bar_builder.py`、`store/parquet_io.py`、`scripts/`（pin_tls / backfill / crosscheck）。

  总量少 1 手），已用 `test_intraday_source_is_provisional` 钉住该性质。
- 端到端回补 rb2610 八天：1m 2070 根 + 三个高周期，落 28 个 Parquet 分区，224KB；
  分区按**交易日**切，08-27 夜盘正确归入 08-28 分区，周末无分区。

### BarStore 落地了 INV-1
M0-A 只有 BarBuilder 和 Parquet，`BarStore.view()` 一直只是文档里的约定。
本段实现 `store/bar_store.py`：喂 1m 增量派生高周期，`view(symbol, as_of)` **在构造时**

写测试时被自己的实现绊了两次，都是真缺陷（不是测试写错）：
1. 时间倒流被去重分支吞掉了 —— 本该抛错（Feed 契约是 close_ts 单调不减，倒流说明上游排序坏了）。

## 2026-08-28 — M1 指标 + 形态 + 单级别预警

分四段做：M1-a 增量指标 → M1-b 白名单表达式引擎 → M1-c 结构原语与插件 → M1-d 规则引擎与推送。

### 先把"口径"定死（ADR-0006）
"MA20 是多少"没歧义，但 EMA 播种、MACD 柱是否 ×2、BOLL 标准差除 n 还是 n−1、
Wilder 与 EMA 的 alpha —— 国内外软件各不相同。规则阈值（`rsi(14) < 45`）是照着屏幕写的，
口径不一致会让规则不触发或乱触发，而且**极难排查**，因为两边都"没错"，只是定义不同。
本项目取：EMA 用 SMA 播种、MACD 柱 = 2×(DIF−DEA)（国内口径）、BOLL 除 n、
RSI/ATR 用 Wilder（alpha=1/n，不是 EMA 的 2/(n+1)）。

### 对拍要"独立"才有意义
验收写的是"增量结果与全量重算逐点一致"。若参照实现复用增量类，就是自己跟自己比。
所以 `tests/test_indicators.py` 里的 `*_ref` **故意写成朴素的每点从头重算**（O(n²)），
与增量实现完全独立，两个市场的真实行情各跑一遍，相对容差 1e-9。

### 预热期必须是 None，这不是洁癖
拿 0 当"还没算出来"，`close > ema(close,60)` 在预热期恒真，数据刚接上的头 60 根会疯狂误报。
于是整条表达式链路做**三值逻辑**：None 具有传染性，`is_satisfied` 把 None 判为不成立。
`and` 遇到明确的 False 仍直接判假（否则预热期什么都判不了），`or` 遇到 True 直接判真。

同一条道理贯穿到底：event 模式的边沿判定里，None **不算**"上一根不成立"——
否则每条规则刚上线都会先误报一次。推送格式化里预热值显示破折号而非 0。

### 沙箱：规则是配置，配置即代码
规则来自 YAML，所以表达式引擎不是"eval 加黑名单"，而是 `ast.parse` 后**按节点类型白名单**放行，
再自己走一遍求值。属性访问（`x.__class__`）、下标、lambda、推导式、海象、星号展开、
`**` 幂运算（`2**(10**9)` 能挂死线程）全部在**编译期**拒绝；未注册的函数名与未知变量名同样在
编译期报错 —— 一条打错字的规则应该启动时炸掉，而不是盘中静默不触发。16 种逃逸写法各有单测。

### 真跑才暴露的一个复杂度缺陷
`scripts/watch.py` 首次真跑，预热 2000 根竟然花了 **5 分半**。
查下来是 `IndicatorCache` 每次求值都**从头遍历整个窗口**去找没喂过的样本 ——
结果完全正确、`update` 调用次数也完全正确，所以**任何按结果或按调用次数写的测试都测不出来**。
但复杂度是 O(窗口长度)，在 M2 的回测里会直接退化成平方复杂度。
改用 `bisect` 定位起点后是 O(log n + 新增根数)。

护栏也重写了两次：第一版数 `update` 调用次数 —— 旧实现下次数一样，测了个寂寞；
第二版计时 —— 余量太大挡不住。最终用一个记录"是否逐个访问旧样本"的序列包装类，
并**特地把旧实现放回去验证过它确实会失败**（旧实现 201 次逐个访问，新实现 0 次）。

### 期货分支真跑：预热之后忘了给游标播种
`watch.py` 第一次带上期货夜盘跑，日志里刷出 **34 条"1m bar 时间倒流"**。
不是数据源的问题：预热用 `by-count` 拉了 800 根、已入库到 21:41，
而 `PollingFeed` 的 `BarCursor` 是空的，首轮轮询就把 17 根重叠窗口当成新数据全发了一遍。
**重叠窗口本是用来查缺口的，没有游标就变成了重发历史。**

讽刺的是 `BarCursor.seed()` 正是 M0-B 为这个场景加的 —— 但只给 OKX 的 WS Feed 接了
`resume_from`，`PollingFeed` 压根没这个参数，`watch.py` 也没传。
补齐：`BarStore.resume_map()` 给出各标的已入库位置，两个 Feed 都接 `resume_from`。

顺带确认兜底是有效的：`watch.py` 里"单根 bar 出错只跳过并吼一声"的保护把这 34 根挡住了，
盯盘没有半夜整个退出 —— 但它吼得足够响，所以问题当场就被看见了。这正是想要的行为。

### 另外两处自己绊到的
- `pin_bar` 原本判"另一侧影线 ≤ 实体"。实体趋近 0 的十字锤会被判掉 ——
  那等于要求另一侧影线必须为 0。改成影线之间的相对比较（另一侧 ≤ 长影线/ratio），对小实体稳健。
- `config/rules/` 里放着 M2 的多级别样板，导致 M1 加载器一启动就**全盘失败**。
  这不是加载器太严，而是目录用错了：`config/rules/` 会被真加载，
  尚不支持的样板属于文档。已移到 `docs/examples/m2-trend-pullback.yaml`。
  加载器保持 fail-fast —— 静默跳过坏规则等于让人以为自己被覆盖了，其实没有。

## 2026-08-28 — M2 多级别规则引擎【核心里程碑】

分五段：模型与加载 → 状态机 → 引擎接入 → SQLite 持久化 → ReplayFeed 与红线对拍。

### 没有做成"两套引擎"
最容易走偏的一步是：M1 已有单级别引擎，M2 再写一个多级别引擎。那样会立刻产生两份
求值时机、两份去重、两份冷却，而且它们迟早不一致。

做法是把规则模型泛化成**有序条件链路**：`conditions` 的顺序就是链路顺序，最后一条是扳机。
长度 1 就是 M1 的单级别规则。于是 M1 的规则一个字都不用改，引擎只有一个（ADR-0007）。
状态机里真正的状态是 `stage`（已满足到第几段），`IDLE/ARMED/COOLDOWN` 只是给人看的投影。

### 记账与判定必须分两步（差点写错的地方）
一开始想的是"扳机 bar 收盘就把各级别都算一遍"。但那样 15m(setup) 与 5m(trigger) 同刻收盘时，
扳机读到的是**上一根** setup 的结果，信号整整晚一拍。

正解是分两步：任何周期的 bar 收盘都**记账**（每根只求值一次，指标缓存因此可单向前进），
只有扳机周期的 bar 才跑状态机**判定**；而且要先把一批同时收盘的 bar 全部记完账再判定。
所以引擎入口是 `on_bars(批)` 而不是 `on_bar(单根)`。

### 顺着挖出 BarBuilder 的一个时序缺陷
写第一条多级别测试时它就是不触发。查下来是 `BarBuilder` 只在**桶切换**时才吐高周期 bar ——
5m 桶要等下一根 1m 到达才出现。可墙钟分桶下，`close_ts` 恰好等于桶边界的那根 1m
**就是**该桶最后一根（更晚的必然落进下一个桶），完全可以当场收盘。

不改的话每条多级别规则都晚一根，连 `role_bars` 与去重键都会错位。改了之后
M0-A 的对拍测试仍然全过 —— 桶的**内容**没变，变的只是它**何时**被吐出来。

### 自己写的冷却语义有个瑕疵
第一版把"解冷那一根"消耗掉了（只解冷、不判定）。结果实际冷却比配置多一根 bar，
而且多出的时长还随周期变化：5m 周期多 5 分钟，1h 周期多 1 小时。
`cooldown: 30m` 就该是 30 分钟，已改成解冷那一根继续参与判定。
这个瑕疵是被 M1 的一条老测试（`test_cooldown_uses_bar_time_not_wall_clock`）逼出来的 ——
它在重构后失败了，而失败的一方是新实现。

### YAML 1.1 的坑：`on:` 是布尔
`ast` 那关过了，YAML 这关没过：PyYAML 把裸键 `on:` 解析成 **`True`**（`yes`/`no`/`off` 同理）。
而规范里条件键就叫 `on:`。M1 时因为加载器有 `timeframe:` 兜底，`cond.get("on")` 返回 None 也没事，
所以一直没暴露；M2 一上来就每个规则文件都报"缺少 on"。加载器现在两种键都收。

### 红线是怎么保证的
"replay 与 live 逐条一致"不是靠对拍对出来的，是靠**引擎全部时间取自 `bar.close_ts`**：
冷却比较 close_ts、TTL 数扳机 bar 根数、信号时间戳取 close_ts，没有一处读系统时钟。
为此专门写了一条测试：把 `time.time` / `time.monotonic` / `datetime.now` 全部换成会爆炸的桩，
整条链路仍要跑通。这比事后比对更能防住回归。

另一条容易忽略的：**跨标的的信号先后本来就不是确定量**（各标的状态互相独立，先到后到
不影响各自结论）。所以比对 replay 与 live 必须**按标的分组后再比**，直接比列表会假失败。

### 重启的两条路不能混
- 无存档（首启）：`prime` —— 只喂指标与条件日志，**不发信号**。否则等于把几十小时历史当实时报一遍。
- 有存档（重启）：`resume` —— 游标之前的只用于重建 BarStore 与指标，
  游标之后的（= 停机期间漏掉的）补判补报，这就是"不丢报"；"不重报"靠持久化的去重表兜底。

写测试时先想当然地"宁可多喂"，结果撞上 BarStore 的时间倒流校验 ——
那个校验是对的，缺的是**没有定义清楚重启该喂哪些 bar**。补成了 `RuleEngine.resume()`。

### 已实现
`rules/`（model 泛化 / loader 重写 / state 状态机 / engine 记账判定）、
`store/runtime_store.py`、`feed/replay.py`、`scripts/replay_check.py`、ADR-0007，
`scripts/watch.py` 接上持久化与重启补判。单测 298 → 363 项。

## 2026-08-31 — M3 Web 只读面板 + 信号质量统计

### 一个岔路：前端不按原架构做
ARCHITECTURE §7 原写 Vite + React + TS。真到落地时开发机只剩 6.1G 磁盘、2 核 4G，

代价写清楚了：P1/P2 交互复杂起来可能要重写前端。

### 由此逼出的一条设计约束：能算在服务端的就算在服务端
K 线上的信号标注第一版写在前端 JS 里。写完才意识到 M3 的验收
"图上标注的信号点与 SignalStore 记录逐条对得上"**根本没法测** —— 它活在浏览器里。

改成 `/api/markers` 由服务端出标注点、前端只负责画。这条验收立刻变成一个可单测的
服务端不变量：每条记录要么有标注、要么进 `dropped`，不重不漏；每个标注的分桶必须
真实存在于该周期序列中，且与引擎用同一套墙钟分桶。**不做就近吸附** ——
吸附会让标注落在一根它并不属于的 bar 上，图看着好看、结论是错的。

### 统计口径：四个最容易把结论做假的地方
"胜率 62%" 极易被做假，而且做假的人往往没有恶意 —— 默认值就是那样。ADR-0008 定死四条：

1. **入场价默认取信号次根 bar 的开盘价**，不是信号那根的收盘价。信号在收盘时才成立，
   那个价已经过去、成交不到。用它统计对"放量突破"这类信号系统性偏乐观。
2. **同一根同时触及止损与止盈时一律记止损**。bar 数据给不出先后，取止盈就是在给自己发奖。
3. **成本按双边扣，且默认 0** —— 默认得到的是毛收益，报告里会把这个参数原样打出来。
4. **`neutral` 不进胜率**：它是"去看一眼"的提示，不是方向判断。

拿真实数据跑出来的第一份报告就给了负面结论：demo 规则 43 条信号、胜率 41.9%、
期望 -0.017%、86% 的信号是持有到期而非触及止盈。这正是这个工具存在的意义。

### 真跑逼出来的三个缺陷
- **SQLite 连接是线程绑定的**。Web 与引擎同进程时 FastAPI 把同步端点丢进线程池，
  第一次冒烟就炸了。改成 `check_same_thread=False` + 锁串行化 ——
  WAL 只解决进程/连接之间的并发，解决不了同一个连接被多线程同时使用。
- **每次正常退出都打一段 ERROR 回溯**：我用 `task.cancel()` 掐 uvicorn，
  它的 lifespan 任务就抛 CancelledError。改成 `should_exit` 优雅关停。
  这种"正常路径上的 ERROR"最有害 —— 它训练人忽略真正的报错。
- **面板在新进程启动时图表几乎是空的**：预热的历史没落盘，只有启动后的 bar 能画。
  信号点没有上下文可看，"K 线回看"就名不副实。补成预热后把各周期序列一并落盘（幂等）。

### 前端 351 行 JS 的回归保护
无构建的代价是没有类型检查也没有测试框架。用 node 做了**桩化冒烟**：
把 DOM / fetch / 图表库全换成桩，把 `boot()` 完整跑一遍，断言接口名没写错、
渲染不抛、时区按市场渲染、预热值显示破折号而非 0。收进 pytest（无 node 时跳过）。

第一次跑它报"信号列表渲染失败"——查下来是**我的断言写错了**（`77,000.5` 而非 `77,000.50`，
`toLocaleString` 的 `maximumFractionDigits` 不补零），代码没问题。

## 2026-08-31 — M4 策略层 + 纸上撮合

分四段：Intent 与仓位定量 → 风控闸 → 纸上撮合 → 接线与验收。

### 开工第一件事：把口径焊死在一起
纸上撮合最容易变成"自我安慰机器"。所以动手前先把 `stats.outcome._risk_distances`
提成公开的 `risk_distances`，让 `trade.strategy` **直接调它** —— 止损位在两边只有一个定义。
出场判定也逐条对齐，并写了一条对拍测试：滑点费用归零后，
撮合与统计的出场原因、出场价、出场时刻必须逐字段相等。

这条测试立刻抓到了我自己的错：我让开仓那一根**不判出场**，理由写的是
"用同一根的高低判出场等于偷看"。想错了 —— 以这根的开盘价入场后，这根 bar 随后真的走过了
它的高低区间，触及止损是真实发生的。统计侧的做法才对。顺带 `horizon_bars=N` 的含义也统一成
"含开仓那根在内持有 N 根"，否则同一条信号在两边的持有时长差一根，收益永远对不上。

### 真跑两次才明白风控该放在哪一层
第一次跑 `paper_run`：**44 条信号，一笔都没成交**，全被 `per_trade_notional` 拒。
查数字才明白：BTC 的 ATR×1.5 止损距离只有 ~0.1%，要吃满 0.5% 的风险预算需要
**5.2 倍名义杠杆**，必然撞穿 30% 的单笔名义上限。

第一次修：把单笔名义上限传给定量层先截一刀。再跑 —— **还是 44 条全拒**，
这次是 `symbol_exposure`（25% 比 30% 更紧）。

两次都是同一个病：**定量层不知道自己身处什么约束里**。最终改成把三个硬上限的剩余额度
（单笔名义、该品种剩余、总敞口剩余）一并算给它，取最紧的那个。
由此得出一条写进 ADR-0010 的原则：**风控闸天天拦，说明定量层没做好** ——
它应该是兜底，日志里出现拒单就该意味着异常，而不是噪声。

### 第一份结果是负的，而且合理
44 条信号全部成交后：权益 -1.13%，胜率 11.4%，**36/44 直接被止损打掉**，
手续费 437 吃掉了 915 亏损里的近一半。

这不是代码问题，是口径问题：ATR×1.5 在 1m BTC 上就是 0.1% 的止损，完全落在噪声里。
正是统计页那张「价格走到了哪里」要说的事 —— 平均浮盈只走到止盈距离的 18%，
平均浮亏只走到止损的 31%，两头都够不着，说明止损止盈的尺度与这条规则的波动不匹配。

### 面板上又抓到两个（还是靠截图）
- 只读模式下账户数字**全是空的**。明明 `trade_state` 已经落盘，复盘时正是要看账户。
  改成从落盘快照复原，并标明"最后一次运行的快照"而不是当下状态。
- 旧快照没存 `initial_cash`，我让它默认成 0 再算出个 **"收益率 +0.000%"**——
  实际是 -1.134%。这又是 ADR-0006 那条老道理：**未知不能显示成 0**，
  会被当成"不赚不赔"读。改成算不出就给 None，面板显示破折号。

## 2026-08-31 · 补节假日表，顺手挖出一个正在发生的 bug

### 补数据之前先发现数据补了也不生效
任务是「把 `holidays` 填上」。填之前照例先读 `calendar.py`，结果发现
`in_session()` 只把时间戳换算成「当日第几分钟」去比 session 区间，**完全不看日期**。
也就是说周六上午十点、国庆节上午十点，它都答 True。

这不是潜在风险，是**当时就在发生**的：健康面板每个周末都把期货全报成「数据滞后」
（因为它以为在盘中却收不到 bar），`PollingFeed` 也整个周末空转拉空数据。
只是没人周末盯着面板看，所以一直没暴露。

修法是把判定拆成三级：自然日是否开市 → 该节是不是夜盘 → 夜盘归属的下一交易日是否开市。
跨零点节的凌晨部分单独一路：它属于**前一自然日**开的那场夜盘，
所以 `AU.in_session(周六 01:00)` 应为 True（周五夜盘的尾巴），而周一 01:00 为 False。

### 节假日前夜不开夜盘，周末不是这么回事
容易混的一条：夜盘归属下一个交易日，所以**法定节假日前最后一个交易日不开夜盘**
（9/30 白天照常，晚上不开）。但周五夜盘照开，它归属下周一。
`opens_night()` 就是这条规则：往后找下一个开市日，中间要是夹着节假日就不开。

另一条本来想当然、查完发现相反的：**调休补班的周六对期货不适用**。
国务院把某个周六算作上班日，期货市场照样休市。所以不需要补班日清单，
`is_trading_date` 只看「是不是周末」和「在不在假期表里」。

### 数据来源：两个独立来源交叉核对
2026 年假期取自两个互不相干的公开日历 API，33 个休息日**零分歧**，
其中 19 个落在工作日（周末本来就休，不用重复列）。条目里写了出处注释。
仍然在 ROADMAP 留了一句：**上线前与交易所公告再核一次** —— 交易所偶尔会
对某个假期的夜盘安排单独发文，公开日历 API 不覆盖这一层。

### 又是 YAML 的类型坑
填完跑自查，13 项里挂了 3 项，全是节假日相关，周末那几项全过 —— 这就把故障点
夹到了「假期匹配」上。打印一看：

```
前3个: [datetime.date(2026, 1, 1), datetime.date(2026, 1, 2), ...]
```

PyYAML 把不带引号的 `2026-01-01` 自动转成了 `datetime.date` 对象，
而 `holidays` 是 `frozenset[str]`，比的是 `date.isoformat()`。
**永远匹配不上，而且不报任何错** —— 假期表写了等于没写。
跟 M2 那个裸键 `on:` 被解析成布尔 `True` 一模一样的家族。

修在构造处（`from_config` 统一归一 date/datetime/str），不是修在某个调用点，
免得下一个从别处构造日历的人再踩一次。并且专门加了一条测试直接喂
`dt.date` 对象进去 —— 这类 bug 的危险之处在于**静默**，没有测试盯着就发现不了。

2026 假期表、日历回归测试 13 项（单测 487 → 500，ruff + mypy strict 全绿）。

`main_variety_codes` 要传 **`rb9999`**，传 `rb` 或 `rb8888` 返回 `{"code":0,"data":null}` ——
**成功状态码配空数据，不报错**。这已经是本项目第 N 个"静默空"了，所以解析函数对空结果直接抛。

拼接本身的关键是**锚点**：换月价差必须拿两个合约的**同一根 bar** 算。

**意外收获**：拼出来的 61 个交易日里恰好 2 天只有 225 根（缺夜盘），

第三件事是试算也得过同一道门。它不改任何东西，但会按请求读任意标的的全量历史

### ④ 带状图：选了不加持久化的那条路

唯一的设计约束是**不能出现第二条求值路径**（ADR-0007）。所以给引擎加了个

## 2026-08-31（晚）· 拿真需求比对代码，补三个缺口

用户描述了自己的实际打法："看大做小"——大级别定方向，小级别找买点（价格贴近小时、
日线均线附近），最好分钟双底或者 5m 金叉后出现至少一个箱体，然后预警。

先把这套原样写成规则跑了一遍：主干**是通的**，4 级链路在 rb 主连 3 个月数据上出 39 条信号。
但逐条验证下来有三处写不出来，而且都不是"我猜的"，是编译器当场报的：

```
❌ prev(swing_low(5))       → 未注册的函数
❌ on: 1d                   → 不是固定长度周期，暂不支持日线规则
❌ 5m 那刻的价格 vs 1h 均线  → 一个条件只能看自己那个周期
```

### 顺带查出一个"编译通过、上线才炸"的洞
探跨级别写法时试了 `ema(close, 60, '1h')`，**它编译通过了**。而 `_ema` 只收两个参数——
运行期第一根 bar 就 `TypeError`。`config/rules/` fail-fast 加载的全部意义就是坏规则
进不了生产，这类错误却偏偏能溜过去。给 `FuncSpec` 挂上 `inspect.signature`，
编译期 `bind` 一下就解决了。顺手也拒掉了 `f(**d)` ——
它的 `keyword.arg` 是 `None`，求值器会静默丢掉，参数凭空消失还不报错。

### `prev()`：数据一直都在，只是没暴露
`swing_low` 返回的 `Level` 内部本来就带 `cur` 和 `prev`（`cross_up` 一直在用），
表达式层从没开这个口。加一个 `prev(x)`，双底立刻能手写：
`abs(swing_low(5) - prev(swing_low(5))) / close < 0.002`。

又包了 `double_bottom(n, tol)` 语法糖，但**多做了一件事：查颈线**。
没有像样反弹的两个相近低点不是双底，是横盘——不查这个，横盘会被当成双底满天报。
为此把 `_swings` 改成返回 `(下标, 价格)`，才能看两个低点之间有没有真正的反弹。

### `at()`：一个特殊形式，胜过三十处签名改动
本来打算给每个指标加可选周期参数 `ema(close, 60, '1h')`。写到一半发现不对：
`sma/ema/atr/rsi/macd_*/kdj_*/boll_*/highest/lowest/swing_*/consolidation/...`
三十多处签名，而且以后每加一个原语都要记得再加一次，还表达不了
"整段换级别"（`at('1h', a and b)`）。

改成求值器里的**特殊形式** `at('1h', <表达式>)`：第二个参数不先求值再传，
而是在切换后的上下文里求值。一处改动解锁全部现有和将来的函数。

关键是别把它做成一个能偷看未来的口子。`at()` 复用**同一个 BarView**，
截断位置完全一致——5m 那根收在 10:05 时，1h 侧看到的是 10:00 收盘那根。
写了专门的测试钉住"前 12 根 5m 落在第一根 1h 收盘之前，at() 必须是未知"。

**最需要小心的是漏派生**：规则里写了 `at('1h',...)` 而 BarStore 没派生 1h，
后果不是报错，是该级别恒为空序列 → 指标恒 None → 条件恒"不成立" ——
一条信号都不报，毫无提示。所以：周期必须编译期可知（不接受变量），
`Rule.required_timeframes` 自报家门，`store_timeframes(rules)` 成为建 BarStore 的唯一入口，
`_ViewSource.bars_at` 取不到就当场抛。

**这个近似原来不是无害的**：同一策略，"1h 收盘时判贴近均线" vs "5m 那刻判贴近"，
在同一批数据上是 41 条 vs 37 条信号。

### 日线：难点不在聚合，在归属
`DayBuilder` 与 `BarBuilder` 并列而不是复用。高周期靠 `ceil(close_ts/period)` 算桶边界，
落在边界上那根当场收盘；日线没有墙钟边界——交易日长度不固定（有无夜盘、节假日前后都不同）。

分桶键是 `trading_day`，不是自然日。**夜盘归属下一交易日**：08-27 21:00 那根属于 08-28，
与 08-28 的日盘合成同一根日线。按自然日切会把每个交易日劈成两半，而且不会报任何错。
上午刚补的日历正好把这条准备好了。

代价是日线只能在**日期键变化时**收盘，比真实收盘晚一根。实际影响很小：
期货下一根是 21:00 夜盘（已属下一交易日），所以上一日日线在下一交易日一开盘就可用，
空窗只落在 15:00–21:00，那段本来没行情。

还有个小陷阱：`D1.seconds` 是 0（表示不可墙钟分桶），几处排序按 `seconds` 排会把日线
排到 1m 前面。加了 `Timeframe.rank` 专供排序。`/api/markers` 的分桶也要分路径——
日线改成"落到收盘不早于该信号的第一根日线上"，与 DayBuilder 归属一致，仍不是就近吸附。

### 收尾：用户原话里的每一条都写进一条规则

## 2026-09-01（续四）· 九宫格

用户选了方案 A，并且要求九个周期：`1m 5m 15m 30m 1h 4h 1d 1w 1mon`，同标的、点一格放大。

### 先补周线月线（枚举里根本没有）
`Timeframe` 只到 `1d`。周/月与日线同类：**没有墙钟桶边界，只能按自然日历切**。
把 `DayBuilder` 泛化成 `CalendarBuilder(symbol, timeframe)`，分桶键按周期算。

两个键设计上的坑，都是"不踩到就永远发现不了"的那种：
- **周键必须用 ISO 年**（`isocalendar()[0]`），不是日历年。12-29 属于次年第 1 周；
  用日历年会得到 `2025-W01`，字典序排在 `2025-W52` **前面** ——
  而时间倒流检查直接比字符串，于是凭空炸出"时间倒流"。
- **月键要补零**：`2026-9` 字典序排在 `2026-10` 后面。

真数据验证：rb 主连 20805 根 1m → 61 日 → 13 周 → 3 月，
周线收在周五 15:00、月线收在当月最后交易日，且月与月首尾相接。

`DEFAULT_TIMEFRAMES` 也补上日/周/月 —— 不补的后果就是那几格静默停更，
和几小时前"行情连不上"完全同一类。

### 九宫格本身
9 个图表实例懒建复用；换标的只换数据。几个细节：
- **每格 220 根**，不是单图的 1500：小格子里塞 1500 根就是一团黑，看不出形态。
- **信号标注每格都画** —— 同一条信号在 1m 和 1d 上落的位置不同，那正是要看的东西。
- **小格禁用拖拽缩放**，放大后才开：小格里误拖一下视图就乱了。
- 放大 = 那一格铺满、其余 8 格 `display:none`，再点还原。
  **不是切回单图页** —— 看完这格还要回到九宫格继续扫。
- lightweight-charts 不会自己跟随容器尺寸，放大/还原/切页都要显式 `applyOptions`。

### 一个桩化冒烟根本测不出的 bug
插「九宫格」按钮时，字符串替换的缩进差了两格，**静默没匹配上**，
按钮压根没进 index.html。然后：

- 桩化冒烟 **绿**

原因是 DOM 桩的 `get(sel)` 对任意选择器都新建一个节点返回 ——

## 2026-09-01（续五）· 15s，以及两条"接口说支持"的验证

用户先要把九宫格第一格换成分时，我做完服务端分时（当日 1m 折线 + 均价线，

这个项目已经被"接口静默返回看似合理的东西"坑过好几次（`main_by_date` 的

## 2026-09-01（续六）· 换回分时

用户看过 15s 之后改回分时。15s 那条链路整条撤掉（`Timeframe.S15`、`OKX_BAR` 条目、

不留死代码。

分时那段服务端代码是之前写好又删掉的，这次原样拿回来。三个决定值得记：

- **分时不进 `Timeframe` 枚举。** 它不是一个"周期"，是当日 1m 的一种画法。

- **取"数据里最后一个交易日"，不是墙钟今天。** 数据可能是陈的（进程没跑、周末），

截图确认分时格横跨 21:01（前一晚夜盘）→ 15:00（当日收盘）——
完整一个期货交易日含夜盘，这正是 `trading_day` 该起的作用。

这已经是今天第二次栽在"字符串替换缩进/上下文不匹配、静默失败"上

## 2026-09-01（续七）· 「期货连上了，但面板找不到期货」

用户报：期货行情已经连上，但盯盘显示的还是加密，下拉框也找不到期货数据。

### 排查
先把每个标的的各周期数据量列出来：

```
CN.CFFEX.IF2609    分时=0    1m=0      1d=0     ← 一根都没有
CN.DCE.m2701       分时=0    1m=0      1d=0     ← 一根都没有
CN.SHFE.cu2610     分时=0    1m=0      1d=0     ← 一根都没有
CN.SHFE.au2610     分时=20   1m=302    1d=3
CN.SHFE.rb2610     分时=20   1m=2371   1d=9
```

**5 个期货只有 2 个有数据。** 再看 `watch.py` 怎么挑标的：
`wanted_symbols(rules, registry)` —— 只取**出现在某条规则 `universe` 里**的。
现有规则只覆盖 BTC/ETH/rb2610/au2610，所以另外三个从来没被采集过。

### 这不是 bug，是两处设计对不上
- 面板下拉框列**全部注册标的**（我为了能看主连改的）
- 盯盘只采集**规则涉及的标的**（合理：没人盯的东西不该白轮询）

两者都对，但合起来就产生了这个体验：列表里有、选中是空图、空状态只说"没有数据"。
用户能得出的唯一结论就是"期货连不上"。

### 修法：把差异标出来，把空状态说清楚
- `/api/meta` 每个标的多一个 `watched`（是否被某条规则的 universe 覆盖）
- 下拉框标「**· 未盯**」，和已有的「· 主连」并列 —— 两个标记各回答一个问题：
  主连 = 不可下单；未盯 = 盯盘不采它的行情
- 空状态分两种说法：没人盯 → "没有任何规则盯 X，所以盯盘进程**不采集**它的行情，
  把它加进某条规则的 universe，或用 backfill.py 回补历史"

**空状态要说清楚为什么空**，这条今天已经第三次派上用场了
（前两次：图表被 canvas 盖住、九宫格 15s 那格）。

### 顺带又一个 flex 坑
空状态消息里加了 `<b>` 之后换行全乱 —— `.chart-empty` 是 flex 容器，
"文本 + `<b>` + `<br>` + 文本" 会被拆成好几个 flex item 排成一行。
裹进一层 `<div>` 就回到正常行内排版。截图当场看到，读代码看不出来。

## 2026-09-01（续八）· 凭据每次都要重配，和"一个源挂了全停"

用户两句话，暴露两个不同层次的问题。

### 「每次本地都要重新配一次数据源 key」
先问有没有前端配置界面 —— 没有，而且**不该做**：面板没有鉴权，
"改规则文件"和"写 API 密钥"是两个风险等级，密钥还会经 HTTP 传输、
读回显示时又会暴露一次。

但痛点是真的，根因比"没界面"更基础：所有文档教的加载方式是
`set -a; . ./.env; set +a` —— **bash 专有写法，Windows 上没有对应物**。
所以他每开一个终端都在手动 `set` 环境变量。

改成脚本自己读。查找顺序 `SIGDESK_ENV` → `./.env` → **`~/.signal-desk/.env`**，
最后那层是真正解决问题的一层：**分发包里不含 `.env`**（凭据不进包的既定约定），
所以每换一个新包、解压到新目录，项目内那份就没了。放用户级目录只配一次。

两条纪律写进代码：**已经在环境里的键永远不覆盖**（否则"我明明 export 了却不生效"
极难查）；**诊断只打印键名不打印值**（值进了终端就进了滚动缓冲区）。
`setup_env.py --show` 只回答"有没有配"。

顺带被自己写的测试抓到一次：`.env.example` 里还留着真实行情主机名 ——
之前只在打包时用 sed 替换，源文件没改。在源头修掉，打包脚本那段 sed 也不需要了。
**测试写在"约定"上（不该有真值），而不是写在"当前实现"上，才抓得到这种残留。**

### 「一个行情源连不上就整体启动失败」
这条更严重。他那台机器 OKX 被 DNS 污染，结果**连能用的期货也盯不了**。

`run()` 里两个市场的历史拉取是顺序执行、任一抛错就整个失败。
改成按市场降级：一边失败只警告并跳过那一边，两边都挂才算真的起不来，
并说明排查方向。缺凭据单独判、单独提示缺哪个键、怎么配 —— 不再抛一个裸 `KeyError`。

验证用了两种真实故障，不是 mock：
- 抽掉 `.env` → `⚠️ 缺少 QUOTE_API_BASE、QUOTE_API_KEY，本次不盯期货`，加密照常
- 往 `/etc/hosts` 写 `169.254.0.2 www.okx.com`（复刻他那台的污染）

两次都在验证后立刻还原了 `.env` 和 `/etc/hosts`。

## 2026-09-01（续九）· 多周期十字线同步

用户两条：放大后 Esc 关不掉；能不能 shift+单击出十字线、九格同步对比。

### Esc
放大后没有可见的关闭按钮，只能双击 —— 全屏状态下确实不直觉。
挂了个 document 级 keydown：**先解除十字线锁定，再退出放大**，
两件事都是"我想回到上一层"，按同一个键、分两步走。

### 十字线同步：两个必须处理对的点
**① 跨周期时间对齐。** 1m 上的 10:03 在 1d 上根本不是一根 bar。
把原时刻直接塞给日线图，`setCrosshairPosition` 要么不显示、要么落在错的位置。
正确做法是二分找"最后一根 `time <= 目标`"—— 那就是**包含该时刻的那根**。

真实浏览器验证（锁定 30m 的 22 May 10:00）：
```
15m / 1h  → 22 May '26 10:00
1d        → 21 May '26 15:00   ← 包含它的日线
1w        → 15 May '26 15:00   ← 包含它的周线
1mon      → 30 Apr '26 15:00   ← 包含它的月线
```
每格同时在价格轴上显示该 bar 的价格，"对比看"要的就是这个。

**② 防回环。** `setCrosshairPosition` 会**再次触发** `subscribeCrosshairMove` 回调。
不加锁就是无限递归，页面直接卡死。用 `G.syncing` 标志，并且放在 `finally` 里解锁 ——
中途抛异常而锁没解，之后所有同步就都静默失效了，那种 bug 极难查。

顶部三格（分时/1m/5m）在锁定 5 月 22 号时没有十字线，是**对的**：
它们的 220 根窗口只覆盖 05-29，压根不含那个时刻。

  同步测试块被插了两份，直接 `SyntaxError: Identifier already declared`。

- 局部变量 `cells` 与外层重名。小事，但同一个文件里 `gcells`/`cells` 并存不好看，

## 2026-09-01（续十）· 均线、成交量，和一个筛选框的真相

### 均线必须算在服务端
用户要均线和成交量。成交量直接用 bar 里的字段，简单。**均线有个一致性陷阱**：
如果图上画的均线和规则引擎用的不是同一份实现，就会出现
「图上明明上穿了、规则却没触发」—— 而 ADR-0006 里 EMA 用 SMA 播种、
预热期返回 None 这些口径，前端随手写一个 `reduce` 是复现不出来的。

所以 `web/overlay.py` 直接复用 `indicators.series` 里引擎用的那两个类，逐根 `update`。
和"撮合口径与统计口径共用 `risk_distances`"（ADR-0010）是同一条原则。

两个实现细节：
- **在完整序列上算再截取**。只把最后 220 根喂给 MA60，前 59 根会是 None，图上左边缺一截。
- **预热期的 null 前端要跳过，不能补 0**。补 0 会在图左端画出一条从零飙起来的假线。

截图当场又抓到一个：四条均线值放进 `chart-head`，把标的选择器和周期按钮挤到换行，
「九宫格」按钮被压成竖排。改成**浮在图左上角**（看盘软件的惯例位置），头部立刻恢复单行。

### 「为什么全部规则有信号，单选每条都没有」
用户问的时候我先去查了数据，而不是猜：

```
信号流里的规则:  multi-level-verify = 44 条,  volume-spike = 6 条
当前加载的规则:  ema-cross-long,  volume-spike
```

真相不是"都是历史信号"，而是**筛选框只列当前加载的规则**：
- `multi-level-verify` 贡献了 50 条里的 44 条，但它早已不在 `config/rules/` 里，
  所以下拉框里**压根没有它** —— 那 44 条永远筛不出来；
- `ema-cross-long` 在列表里，却一条信号都没有 —— 选中当然是空的。

改成 **信号里的规则 ∪ 已加载的规则**，每条后面带信号条数，已删的标「已下线」。
空态也分开说：「规则 X 还没有产生过信号」vs「还没有信号」。

顺带踩了个自己的坑：`fillRuleFilter()` 在 `boot()` 里的调用位置**早于信号加载**，
所以计数全是 0、下线规则也进不来。真浏览器里一跑就看出来了 ——
这种"顺序错了但不报错"的问题，桩化冒烟同样发现不了。

## 2026-09-01（续十一）· 量能均线与 B/S 标

### 量能均线：窗口不是随便挑的
用户要成交量上也有折线，说这样更直观。做的时候顺手确认了一件事：内置规则
`volume-spike` 判的是 `volume > sma(volume, 20) * 2.5`。所以图上那条量均线
**必须也是 sma(volume, 20)** —— 否则你看到量柱冲破了线、规则却没报，
或者反过来，根本无从解释。默认给 VSMA5 + VSMA20，20 那条正是规则用的。

技术上一个要点：量均线必须挂在**成交量那条 priceScaleId** 上，
否则它按价格刻度画，直接飞出画面。

### B/S 标
用户原话：「现在 K 线图上全部是向上的箭头」。确实 —— 箭头只有朝向之分，
他跑的规则全是多头，一屏看下去一模一样。改成圆点 + `B`/`S` 字母。

**中性信号不写字母**：它既不是买也不是卖，硬安一个字母是撒谎，只画灰圆点。

改完立刻撞上一个连带问题：**信号成了圆点，而成交的离场点原本也是圆点**，
同色时（止盈绿圆 vs 多头信号绿圆）完全分不开。所以把成交离场换成箭头，
形成三种互不冲突的形状：

```
圆点 = 信号（B/S 字母）
方块 = 开仓成交
箭头 = 离场成交（朝向 = 平仓方向）
```

这类"改了 A 就撞到 B"的问题，只有把图真截出来看才发现得了。

### 同一个坑踩了两次
均线值放进 `chart-head` 会把标的选择器和周期按钮挤到换行。
价均线那次已经修过（挪到图上浮层），结果加量均线时**又塞回了头部**，
「九宫格」按钮再次被压成竖排。现在两类图例都走同一个浮层。

教训：修完一个布局问题，要把**同类元素**一起归位，否则下一次加东西还会掉进去。

## 2026-09-01（续十二）· 全品种「看大做小」，以及一个夜盘归属的真 bug

### 全品种的第一个设计决定：阈值必须 ATR 归一
用户原来那条规则用百分比：`abs(close - ema)/close < 0.006`。
跑单品种没问题，**跑全品种就完全不成立** —— 黄金日内波动约 0.3%、BTC 约 3%，
同一个 0.6% 对两者是两回事：一个永远满足，一个永远不满足。

改成 `abs(close - ema(close,20)) < atr(14) * 0.8`。ATR 是各品种自己的波动尺度，
用它做分母，一套参数才能通吃 7 个品种。

**验证方式是逐品种试算**：7 个品种价格从 960（au）到 78000（BTC），
全部都能触发（4~51 条），没有出现"某些几百条、某些零条"。这就是归一化要证明的事。
（`consolidation` 与 `double_bottom` 的参数本来就是相对量，无需改。）

### 回补是前置条件，不是可选项
规则用 1h 的 `ema(20)`，需要 20 根 1h ≈ 3.5 个期货交易日。
不回补历史就永远预热不完、一条都不报 —— 这在真机测试里表现为"跑了半天没动静"，
极易被误判成系统坏了。所以测试文档把回补列成**第二步**，并写明各周期需要多少历史。

顺带修了 `backfill.py`：**by-count 跨度一大就读超时**（实测两个月必挂、一周稳过），
而超时是在流读取阶段抛的，看起来像"连不上"。改成内部按周分段拉，分段是幂等的。
au/cu 因为夜盘到 02:30、每天 ~505 分钟，即便分段也要按月跑两次。

### 按标的降级，不是按市场
真跑时 5 个期货里有 1 个历史拉失败，结果**整个期货市场被跳过** ——
上午刚做的"按市场降级"这时显得太粗了。改成按标的：某个品种拉不动就只丢它，
另外四个照常。一个坏苹果不该毁一筐。

### 然后崩在了启动阶段：夜盘交易日归属错了
接上 au2610 之后 `watch.py` 直接抛 `ValueError: 1m bar 时间倒流: 当前 2026-08-31 > 新 bar 2026-08-29`。

查下来是 `MarketCalendar.trading_day` 的真 bug：

```
08-28 23:59（周五夜盘）      -> trading_day = 08-31  ✅
08-29 00:00（同一场的凌晨）   -> trading_day = 08-29  ❌ 应该也是 08-31
```

一场夜盘从晚上开到次日凌晨，**整场同属一个交易日**。原实现对凌晨那段直接返回当天日期，
平日恰好等价（周四夜盘的周五凌晨 → 周五），**但跨周末就劈成两个交易日**：
前半场归下周一、后半场归周六。后果是日线聚合当场报"时间倒流"、Parquet 也分到两个分区。

更值得记的是：`in_session` 一直是按"前一自然日是否开夜盘"判的，**判对了**；
只有 `trading_day` 没跟上。两个判定本该同源却各写各的 —— 这类不一致最难发现，
因为单看任何一个都说得通。

修法是让两段用同一个式子：凌晨段 = `next_trading_date(前一天)`，
夜盘段 = `next_trading_date(当天)`。平日两者等价，跨周末/节假日才见分晓。
补了 9 项回归测试。

**已落盘的数据带着错误的 trading_day**，归错分区的必须清掉重补 —— 清了 `data/bars/CN`
全量重来。这条要记住：**修交易日归属之后，历史数据必须重补，不能只改代码。**

### 基线（不是结论）
7 品种、两个月、持有 24 根 5m、止损 0.4%/止盈 0.8%、单边 1bp：
多头 211 条 / 胜率 51.2% / 期望 +0.030%；空头 128 条 / 34.4% / −0.067%。
样本区间大概率偏多头，且没做样本外验证。写进 TESTING-KDZX.md 时明确标注了"别当结论看"。

### 追记：交易带被画成一条贯穿全图的假线

1. 第一版的空白点放在 `离场时刻 + 1 秒`。那个时刻不在时间轴上，被 lightweight-charts

2. 第二版把空白点放到**真实 bar 时刻**，又发现"前一笔的断点正好落在后一笔的开仓上"

它只把有值的点顺次连起来。既然断不开，就不给它连的机会 —— 改成一笔一条 series、

- **染色定位**比盯着图猜快得多。图上七八条线，颜色一改就知道是谁。
- **数据对不等于画得对。** 这个 bug 骗过了"点数对不对""断点在不在 bar 上"两轮断言，

- 前两版留下的测试没有白写：它们现在断言的是"一笔一条、每条恰好两个点"，
  以及那两条歧路的原因写在测试的 docstring 里，免得以后有人"优化"回去。

## 2026-09-02 · 预警组（网格的第二种模式）

用户的问题很具体：「触发信号的标的显示在哪里，右侧的信号栏里吗？如果有多个标的
触发信号，但是我人工判断后感觉还需要观察，是不是可以有一个预警组的多品种视图」。

信号流是**流水**，回答不了"现在有哪几个值得盯"。而"人工判断后还需要观察"翻译过来
就是一个动作：**钉住**。整个功能里唯一需要人动手的也只有它。

### 最关键的一个决定：组不要维护，用算的

第一直觉是"维护一个数组，新信号 push，满了 shift"。想了一下那条路要处理的东西：
重复加入、手动移除后又被自动加回、重启后错位、淘汰顺序、钉住的怎么豁免……
每一项都是状态同步 bug 的温床。

改成 `组 = 钉住的 ∪ 最近触发的，取前九`，**只有钉住落库**。
淘汰是自然发生的 —— 没有淘汰逻辑，也就没有淘汰 bug。写完发现测试也变简单了：
`build_group` 是纯函数，同样输入永远同样输出，那条断言本身就是这个设计的证明。

### 两条界限

**钉住落库、已读放浏览器。** 看着都是"UI 状态"，性质完全不同：钉住会让盯盘进程
开始采集这个标的，采集端必须看得见；"看没看过"是每个人自己的事，换台机器
重新标一遍无所谓。前者进 SQLite，后者进 localStorage。

**钉住按绑定地址放行，不占用 `--allow-edit`。** 钉住确实是写操作（会多发对外请求），
但 `--allow-edit` 是给规则 CRUD 和试算准备的（任意规则执行 + CPU 放大器），
量级差得远。把日常操作关在那个开关后面等于这个功能没法用。
默认 127.0.0.1 开箱可用，`--host 0.0.0.0` 才拒绝，并给出 SSH 隧道的做法。

顺便想明白一件事：横着扫九个标的时要的根本不是 SMA 值，是"现在多少钱、涨还是跌"。

## 2026-09-02（下午）· 用户反馈的 10 条，统一优化

用户连着问了几个"这是不是 bug"，攒成一批一起改。有价值的不是改动本身，是**为什么这些
问题会同时出现**。

### 一半是同一个根因：标记只回答了一半问题

下拉框里的 `· 未盯` 标记回答的是"有没有规则盯它"，用户读到的却是"这个能看"。
冷启动时这两件事完全不重合：规则盯着 BTC/ETH（`watched=True`），但行情还没接入、
一根 bar 都没落盘，于是下拉框里**干干净净什么标记都没有**，点进去是空图。

再加上默认选中会退到"第一条规则 universe 的第一个标的"——那个多半也没数据。
于是用户打开面板看到的是：一个没有任何标注的标的 + 一张空图。他的结论"这应该是 bug"
完全合理。

修法不是加更多标记，是**让标记回答用户真正在问的问题**：`无数据` / `数据止于 X` /
`未盯` 三个都指向"点进去会是空的"，而不是只讲规则覆盖。再把下拉框分成「有信号」和
「其他已注册」两组 —— 前者是他平时要切的，后者才是"去逛"的。

### 另一半是我自己上一轮弄坏的

预警组重构时把格子的身份从 `tf` 改成了 `key`，`ondblclick` 跟着改了，
但 `zoomCell` 和 `syncCrosshair` **都没改**：它们仍然只遍历 `G.cells`、仍然按 `tf` 比对。
后果是预警组里双击放大和十字线同步双双静默失效 —— 而"放大后才允许缩放"挂在放大上，
所以用户报的是"不支持放大缩小"。

教训很直白：**改了一个东西的身份，就得把所有按身份找它的地方一起改**。
现在加了 `activeCells()`，凡是"对所有格子做点什么"的地方都必须走它。

### 日/周/月只有几根：不是限制，是算术

高周期全部由 1m 聚合而来，1m 回补了 45 个交易日 → 45 根日线、10 根周线、3 根月线。
想看两年日线就得拉两年 1m（每品种约 12 万根），荒谬。

接口原生支持日线（`interval_range=101`），加个 `--timeframe 1d` 就行。
实测 rb2610 日线 45 → **261 根**（该合约上市以来全部）。

中间踩了一个自己挖的坑：过滤"比基础周期更大的"用了 `t.seconds > timeframe.seconds`，
而**日历周期（日/周/月）的 `seconds` 是 0**，于是拉日线时 5m~4h 全被判成"更大"，
一路走到 `BarBuilder` 里炸掉。该用 `rank` —— 它跨墙钟/日历单调。

### 跑两个 watch 会重复报警且不报错

用户问"为啥这么多入口"时才意识到：`watch.py` 没有任何双实例保护。
状态机、去重表、冷却都在同一个 SQLite 里，两个进程各持一份内存态，
同一根 bar 判两次 —— 你会收到两条一模一样的预警，而且没有任何报错。

用 SQLite 里的 pid 记录 + `os.kill(pid, 0)` 存活探测做，**不用 pid 文件**：
那玩意崩溃后会留下，下次启动反而把自己挡在门外。存活探测失败时一律当"还活着"——
误判成"死了"会放行第二个写者，那正是要避免的。

### 测试自己的疏忽：cp 一个 WAL 库会丢数据

造演示库时 `cp data/runtime.sqlite3` 拷出来 0 条信号 —— **50 条都在 `-wal` 里**。
改用 `sqlite3.Connection.backup()` 才对。这条对用户同样重要（备份运行态时会撞上），
已写进 RUN-WINDOWS 的备份一节。

单测 741 → 756。

## 2026-09-02（晚）· 规则评估必须减基准，否则排序是反的

加了突破/反弹两类规则之后跑统计，第一版结论是「breakout-long 最好、kdzx-short
该关掉」。**这个结论是错的**，而且错得很彻底 —— 因为忘了减基准。

先量了样本本身：等权 **+10.05%**（au +8.65%、m +10.98%、BTC +21.33%、ETH +27.49%）。
两个月单边上涨。在这种样本里，任何多头规则都会显得好（市场自己在涨），
任何空头规则都会显得差（一直在逆风）。

改用**超额** = 规则期望 − 随机进场期望，且基准要**按该规则自己的信号分布加权**
（kdzx-long 有 101 条打在漂移最大的加密上，用全样本平均当基准会低估它的顺风）。
排序当场反转：

```
               毛期望     加权基准     超额(1bp)
kdzx-long     +0.034%   +0.057%     -0.043%   <- 之前以为还行
kdzx-short    -0.026%   -0.050%     +0.004%   <- 之前建议关掉
breakout-long +0.075%   +0.053%     +0.002%   <- 之前以为"唯一站得住"
breakout-short+0.011%   -0.058%     +0.049%   <- 之前以为最差
```

**"唯一站得住的 breakout-long"其实几乎全是市场漂移；"该关掉的 kdzx-short"
反而是有边的。**

教训写死一条：**这个项目里任何规则评估都必须同时给出基准和超额**，毛收益单独
出现就是误导。ADR-0008 定了口径（入场价、成本、退出原因），但漏了"跟什么比"。

### kdzx-long 的消融：不是参数问题

八个变体全是负超额：去掉箱体 -0.070%、箱体放宽 -0.070%、箱体缩短 -0.082%、
去掉贴近均线 -0.016%、贴近放宽 -0.017%、只要金叉 -0.038%、只要双底 -0.013%、
换成放量突破扳机 -0.049%。

超额为负意味着**它挑出来的时刻比随机时刻更差** —— 跟市场涨跌无关，不是
"样本偏多头"能解释的。关掉，文件头写清重开条件是「换一段震荡或下跌行情重跑」，
**不是调参**：八个变体已经把参数空间扫过一遍，再调只会拟合这两个月。

### kdzx-short 重做

③双顶/死叉 + ④箱体 换成一段「放量下破前 20 根 5m 区间」，超额 +0.004% → +0.049%。
猜想：等双顶走完再等 12 根箱体确认，反抽那一波已经结束，进场太晚；
突破是"反抽结束"的即时证据。

### 跨周期均线：台阶就是没作弊的证据

在 5m 图上叠 1h / 1d 均线。唯一的技术难点是 **as-of 对齐**：一根 1h 均线的值
只有在那根 1h **收盘之后**才算已知。摊到那一小时的每根 5m 上，等于让 09:00 的 bar
看到 09:59 才收盘的数据 —— 复盘会得出"当时明明看得出来"的错误结论，
而实盘那一刻你根本看不到。

对齐正确的话，图上呈现为**台阶**（1h 线每小时跳一级，1d 线每天跳一级）。
那两条粗线的阶梯形状本身就是"没插值、没泄露未来"的视觉证据。
单测直接断言 `align_as_of` 的逐点输出，包括"第一根参考 bar 收盘前必须是 None"。

单测 758 → 764。
